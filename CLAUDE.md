# QB Evaluator

Weekly-updated NFL QB grade (1-100) built on nflverse play-by-play + FTN charting. The core idea:
separate interceptions by fault (bad throw vs. tipped/receiver-caused, plus "dropped interceptions").
Portfolio project; methodology must be defensible, so every change to the grade is backtested.

## Environment
- Windows, Git Bash, VS Code. Python venv at `.venv` (`source .venv/Scripts/activate`).
- Install: `pip install -r requirements.txt`. Data cached in `data/` (gitignored).
- Run analysis: `jupyter nbconvert --execute --to notebook --inplace qb_backtest.ipynb` (several minutes).
- `qb_backtest.ipynb` is GENERATED by `make_notebook.py`. Edit `make_notebook.py`, then regenerate and execute.
  Never hand-edit the .ipynb.

## Files
- `qb_eval.py`: loading (`load_season`, `PBP_COLS`), counterfactual value models (incompletion/completion/INT EPA
  given situation), `adjust_dropbacks` (stores each adjustment as a delta column `d_int`, `d_drop`, `d_sack`,
  `d_yac`), `recompute_adj` (weights per adjustment), `qb_table` (per-QB aggregation), `add_grade`, `shrink`.
- `backtest.py`: split-half (odd vs even weeks) and year-over-year tests, `bootstrap_diff`, `shrinkage_k`.
- `mixed.py`: ridge-as-random-effects model (QB + defense + offense). Kept for reference; did not help.
- `update_board.py`: weekly live-board refresh (no backtests). Fits the value models and shrinkage k from
  2022-2025, applies them to `--season` (default 2026; `boards/` currently also has a full 2025 backfill), and
  for every week where **every scheduled game is final** (checked via `nflreadpy.load_schedules`; a week in
  progress is skipped, so the latest board is always a complete week) writes two files:
  `boards/<season>_wk<N>.parquet` (CUMULATIVE, season-to-date through week N) and
  `boards/<season>_wk<N>_weekly.parquet` (that week's plays only, shrunk harder with a shrinkage k measured
  from consecutive-game reliability, not a guessed multiplier -- see `backtest.game_pairs_table`). Also writes
  `boards/<season>_interceptions.parquet` (play-level, for QB pages), `boards/<season>_games.parquet` (per-QB
  game log: box score, unshrunk adj EPA/dropback, single-game grade from the weekly board) and
  `boards/team_colors.parquet` (so
  `app.py` never has to call nflreadpy itself). `boards/` is committed; `data/` stays gitignored. Saves EVERY
  QB with >=1 dropback, no minimum -- see "Qualifier" below. `--season`'s data is always refetched fresh
  (`load_season(..., refresh=True)`, which also clears nflreadpy's own response cache for that season, not
  just our local parquet) since this is meant to be the in-progress season; historical seasons stay cached.
  Cumulative boards also carry box-score season totals from `box_score()` (completions, attempts, yards, TDs,
  INTs, sacks, sack yards, passer rating, carries incl. scrambles + designed runs + kneels, scrambles). These
  are CONTEXT ONLY, never grade inputs, and are built from the full pbp (not the graded dropback set) to match
  official definitions; validated against `nflreadpy.load_player_stats` for 2025 (counts exact or within 1-2
  plays league-wide; sack yards stored positive).
- Known quirk: the value models (`HistGradientBoostingRegressor`, no `random_state`) are not bit-for-bit
  deterministic, so rerunning `update_board.py` on unchanged data nudges adj EPA in the 3rd-4th decimal and
  can move a grade by a point or two.
- `app.py`: Streamlit site (leaderboard, QB pages, methodology) reading only from `boards/` -- no network calls
  of its own at all, so it can't fail or hang at startup regardless of nflverse's availability. Routes pages
  via `st.query_params` (`?page=leaderboard|qb|methodology`, `?view=season|weekly&season=<year>` on the
  leaderboard). Leaderboard has a season selector (any season with boards, not just the current one) alongside
  the week selector; switching seasons preserves itself across the view-toggle/sort-header links, which are
  plain `<a>` tags that do a full page navigation, not a Streamlit rerun (`season`/`week` ride along in the
  query string). QB page has its own QB/Season/Week selectors and shows grade, components, Season stats and
  Game log (both labeled CONTEXT ONLY), charting context, and interceptions. Run: `streamlit run app.py`.

## Design rules (app)
- Light theme only, for every visitor: `.streamlit/config.toml` sets `[theme] base = "light"` (a custom theme
  overrides the viewer's OS dark mode). It is the one tracked file under `.streamlit/` (see `.gitignore`).
- Layout: fixed dark navy left sidebar (title "QB Evaluator" ~24px bold white + subtitle, then nav with the
  active item highlighted); light gray page with content on a white card. Under 760px wide the sidebar
  becomes a navy bar at the top of the card and filters go two per row.
- Filters are labeled dropdowns (bold dark labels) in a row above the table.
- Tables: white rows, thin light gray dividers, dark text, bold headers that may wrap, underlined QB links.
- Shading: ONE warm sequential hue (light peach -> deep orange, deeper = better, `warm_bg`) on key columns
  only (Grade, Adj EPA/play, Success %, plus percentile/grade cells on the QB page). Sack %, INT-worthy %,
  Dropbacks stay unshaded. No diverging blue/red. Text stays dark on every shade (worst case 5.5:1, WCAG AA);
  re-check contrast if the endpoints change. Unqualified rows are never shaded.
- No gray-on-gray: every control and nav item must be clearly visible on its background.
- No em dashes in any app text.

## Current model (v2 adjustment, v3 composite) and what the backtests showed (2022-2025)
- Target for every test: predicting raw EPA/dropback out of sample. Baseline to beat: raw EPA/dropback.
- v2 = INT-fault adjustment only, NO garbage-time filter. Slightly beats raw EPA (split-half r .553 vs .546,
  YoY .465 vs .450). Not statistically significant.
- Hurt, do not re-add without new evidence: full drop credit, garbage-time filter, replacing YAC with expected YAC,
  removing offense/team effects. Opponent adjustment was about neutral.
- QBs who changed teams (n=14): no metric predicts their next season.
- Box-score stats tested as additions to v2 (season-grouped CV): only sack rate (+.009) and success rate (+.003)
  helped. Yards, TDs, comp%, ANY/A, CPOE added nothing; adding all of them hurt (-.024). INT rate is ~0 stable.
- v3 composite (see `qb_backtest.ipynb` section 9): added `success_rate` (EPA>0 share) and `total_sack_rate`,
  dropped `cpoe` and `fault_sack_rate`. Individually: success rate predicts almost as well as adj EPA itself
  (split-half r .521, YoY .471); total sack rate clearly beats the FTN-charted QB-fault sack rate (split-half
  -.363 vs -.142, YoY -.436 vs -.346, bootstrap p(better)=1.0 split-half). Combined composite beats the old
  composite on both tests (split-half r .505->.538, YoY .457->.493) and now beats raw EPA YoY, though it still
  trails raw EPA split-half. Chosen post-hoc (after looking at the backtest), like v2 before it; none of the
  deltas clear statistical significance with 4 seasons of data.
- Read-progression metrics from FTN `read_thrown` (past-first-read rate, checkdown rate, EPA on 2nd+ read
  throws) do NOT help: weak and sign-unstable (past-first-read rate is +.05 split-half but -.24 YoY). Not in the
  grade. Still computed in `qb_table` for QB-page display only (process context, not a grade driver).
- FTN charting standards drift by season, so all rates are compared within season only.
- Uncharted plays (FTN lags a day or two) keep raw EPA; `load_season` warns if latest week < 90% charted.

## Grade composite
Weights in `CONFIG["weights"]` (z-scores within season, then percentile to 1-100): `adj_epa_db` .45,
`success_rate` .20, `int_worthy_rate` -.15, `total_sack_rate` -.15, `rush_epa_db` .10. Live board shrinks each
component toward league average with k from split-half reliability (QB adj EPA k ~186 dropbacks). `cpoe` and
`fault_sack_rate` are kept as unshrunk context-only columns on the live board; they no longer drive the grade.

## Qualifier (who gets ranked)
NFL passer-rating-style rule: a QB qualifies with >= 14 dropbacks per team game played. "Team games played"
comes from the schedule (`nflreadpy.load_schedules`), not the week number, so a bye week doesn't unfairly
penalize a team's QB. `update_board.py` computes this per row as `qualifier_dropbacks` (14 x team games played;
flat 14 on the weekly board, since that's always one game) and a boolean `qualified`, and saves EVERY QB
regardless -- it does not filter anyone out. All filtering is the app's job (the dropback slider), but
shrinkage, grading, and the percentile scale are always computed on the qualified population only (in
`update_board.py`'s `grade_among_qualified`), so a handful of mop-up dropbacks can't skew the scale; unqualified
QBs keep their raw (unshrunk) stats with grade/composite left `NaN`. The app shows unqualified rows (when the
slider is low enough) with a "LOW SAMPLE" badge, no rank number, and unshaded cells, never mixed into
percentiles or ranks.

## Cumulative vs. weekly
Two different things, both on the leaderboard (a Season/Weekly toggle) and the QB page (a line + dots on the
same chart):
- **Season (cumulative)** -- season-to-date through the selected week. This is the real ranking.
- **Weekly** -- that single week's plays only, shrunk harder (see `update_board.py` above). Single games are
  noisy; this view exists for context, not for ranking QBs against each other week to week.

## IDs, not names
Every join, filter, and lookup in this project keys on the GSIS player id (the `id` column
`adjust_dropbacks` sets), never on name. nflverse's short display names collide across real players --
2026 has two different "J.Daniels" (00-0039910 Jayden Daniels, WAS; 00-0041251 Jalon Daniels, TB) who are easy
to merge by accident if anything groups or joins on name instead of id. `id = passer_player_id.fillna(rusher_player_id)`,
**not** `passer_player_id` alone: a scramble has no pass, so `passer_player_id` is null and the QB only shows up
as `rusher_player_id` -- an earlier version of this missed that and silently dropped ~250 scramble dropbacks a
season (verified against the pre-bug baseline: Lamar Jackson/Josh Allen/Jalen Hurts/Jayden Daniels dropback
counts and EPA/db all match exactly after the fix). `update_board.py` also restricts the board to nflreadpy
position `== "QB"`, so a trick-play pass by a WR doesn't show up as a quarterback, and overwrites the display
`name` column with the full name from `nflreadpy.load_players()` (`gsis_id` -> `display_name`), falling back to
the pbp short name only if a player isn't found there. The app's QB selector, links, and page routing
(`?qb=<id>`) are id-keyed throughout; every QB with at least one dropback gets a page, qualified or not.

## FTN `read_thrown` codes
Confirmed empirically against the actual charting data (sack_rate/comp_rate/aDOT by code), not just the
nflreadr data dictionary page, because that page has `"0"`/`"1"` backwards from what the data shows:
`1` = first read (EPA .30, highest volume), `2` = second+ read (.17), `CHK` = checkdown (aDOT ~0),
`DES` = designed/screen (aDOT -3, no real progression), `SD` = off-script/scramble drill, `0`/NaN = no read
charted (sacks ~70%, throwaways, non-pass plays; 2022 used NaN instead of `"0"` for this bucket).

## Weekly refresh (production)
`.github/workflows/update_board.yml` runs `update_board.py` on a schedule and commits `boards/` if it
changed (`contents: write`, no other permissions needed):
- **Tuesday 14:00 UTC** -- the normal weekly run, once Monday Night Football is final.
- **Wednesday 14:00 UTC** -- a second pass that picks up any FTN charting that was still lagging on
  Tuesday (`load_season` logs a warning, and additionally emits a `::warning::` GitHub Actions
  annotation, whenever charting for the latest week is under 90%; it does not fail the run).
- `workflow_dispatch` -- manual trigger from the Actions tab (Actions -> Update QB board -> Run
  workflow), for testing or an off-schedule refresh.

Deployment: the app is meant to run on Streamlit Community Cloud pointed at this repo with `app.py`
as the entrypoint. No secrets needed -- it only reads the committed `boards/`. `runtime.txt` pins
the Python version. Community Cloud redeploys automatically on every push to `main`, so a workflow
commit to `boards/` is what actually refreshes the live site.
